# How NextTex works

This document is the internal mechanics: what the parts are, what each one owns, and why the awkward decisions are the way they are. It is for somebody about to change the code. `docs/design.md` is the interface specification, `docs/testing.md` is the test tiers, and the README is what the app is for.

## The shape

One Python process, one event loop, and a folder of ordinary LaTeX files. No database, no queue, no container, no reverse proxy. Everything NextTex knows that is not in your `.tex` files lives in a `.nexttex/` directory inside the project, and everything about the install lives in one state directory outside it.

That constraint drives most of what follows. A single process means anything synchronous in a request handler stops every other browser, every autosave and every collaborator, so work that blocks goes to a thread. No database means the durability story is files, atomic renames and fsync. No container means the code has to cope with whatever TeX, git and Node happen to be on the machine.

```
   browser ──HTTP──┐
   browser ──SSE───┤        ┌──────────── one uvicorn process ────────────┐
   browser ──WS────┤        │                                             │
                   └───────▶│  FastAPI app                                │
                            │    middleware: headers, then the gate       │
                            │    113 routes                               │
                            │                                             │
                            │  SESSIONS: one ProjectSession per project   │
                            │    ├─ CollabStore   the documents           │
                            │    ├─ SyncHub       browser sockets         │
                            │    ├─ PeerNetwork   other installs          │
                            │    ├─ CompileScheduler                      │
                            │    ├─ Agent         one Claude session      │
                            │    └─ Broadcaster   the event stream        │
                            │                                             │
                            │  background: watcher, reaper, rejoin, warm  │
                            └──────────────────┬──────────────────────────┘
                                               │
                    project folder ◀───────────┘        ~/.local/share/nexttex/
                      main.tex, chapters/, figures/       peer.key, settings,
                      .nexttex/  history, trash, collab   registry, token
```

## Starting up

`server/run.py` builds the FastAPI app and serves it on one address or two. uvicorn binds one socket per server object, so "reachable on localhost and over Tailscale" is two server objects sharing one event loop and one application. Loopback is plain HTTP because nothing leaves the machine; anything reachable from another machine is TLS.

**The token is printed to a terminal and nowhere else.** The banner a starting server prints carried the token URL wherever stdout went, and a service's stdout is `server.log` on macOS and Windows and the journal on Linux, so the token sat in clear for the life of the log and the bug report had to redact it. `banner` in `server/run.py` prints the link with its token only when stdout is a terminal; a log gets the address and the command that prints the link on request, `server/run.py --print-url`, which is unchanged and is what the lane and the README use. `update.sh` prints the link at the end only when it too is on a terminal, since run from the update button its output is `update.log`.

The lifespan starts four background tasks and cancels them on the way out.

**The file watcher** tells browsers when files change underneath them. An external edit, a `git pull`, a checkout, somebody's own editor, has to reach the open tab or it will save over a change it never saw. NextTex's own writes must not, or the browser would be told to reload the buffer it just sent.

**The reaper** runs every sixty seconds. It disconnects idle agents, evicts idle sessions, sweeps unreferenced history blobs out of every open project about once an hour, and discards joins nobody answered.

**The rejoin task** opens every shared project so its peers can reach it again after a restart.

**The warm task** imports the agent SDK while nobody is waiting, because that import costs about six hundred milliseconds and was otherwise paid by the first person to open a project after an update.

**Two commits, read at two different times.** `HEAD_AT_BOOT` is read once here, when the process starts, and is the only commit this process can honestly claim to be running. The commit on disk is asked for when `/api/instance` is called, because it moves: an update pulls into the working tree of a server that is already running. They were one field, read at request time, so an install updated and not restarted reported the new commit, matched it against the remote, and called itself up to date while serving the old code.

**The version is a line in a file.** `nexttex/version.py` holds `VERSION = "x.y.z"` and nothing else decides it; `CLAUDE.md` says what the three parts mean and how a push advances them. `/api/instance` reports it as `version`, the update footer's quiet line names it, `server/run.py --version` and `python -m nexttex.version` print it above the two commits, and the bug report leads its install section with it. `updates.check` reads the upstream commit's copy with `git show @{upstream}:nexttex/version.py` after the fetch it has already paid for, so the footer can lead with the number an update would move to; an upstream older than the number gives an empty string, which the footer treats as nothing to say. The number is a fact about the code and not about the build: the interface asset stays keyed to the commit, and the `release` workflow, which runs on a `v*` tag, refuses a tag that disagrees with the file before publishing the commit subjects since the previous tag as the release notes. A release that already exists is brought up to date rather than refused, so a re-run job or a tag pushed again after a history rewrite goes green, and Latest is the highest version tag rather than whichever job finished last. GitHub raises no push event for a push carrying more than three tags, so tags pushed together after a history rewrite run nothing; their releases are then made by hand with the same notes, oldest first.

**Restarting on purpose.** `POST /api/update/restart` exits with the supervisor's code, which is the same mechanism the update path uses: there is no way to ask uvicorn to stop from inside a request, so the exit is the restart. It refuses with 409 where `updates.supervised()` is false, because nothing there would bring NextTex back and a route that leaves the writer with no server is worse than one that says it cannot help. The footer only offers the control when the instance reports `supervised`. On Linux and macOS that is the unit or the agent, both configured to restart on a non-zero exit. On Windows a scheduled task is not a supervisor, a task that ends stays ended, so before it leaves the server starts a detached PowerShell helper, `updates.windows_restart_argv`, that waits for the pid to go and starts NextTex the way it was started: the scheduled task once it has left Running, the Startup shortcut if there is no task, and the same command line hidden with `--log-to-state` failing both. The helper is started with `CREATE_BREAKAWAY_FROM_JOB`, which took the install lane's Windows update leg two tries to teach: a task runs its action inside a job object, everything the action starts is in that job, a job with a live process in it is a task that still counts as Running so `Start-ScheduledTask` did nothing, and when the action's own process exited the job was torn down and the helper with it. Out of the job it outlives the exit and the task is free to start again. A job that forbids breakaway refuses the flag, and the helper then runs inside and does what it can; the server writes which happened to `restart.log` beside `server.log`, and the helper appends its own lines there, one per step and one for a failure, with `Add-Content` rather than a transcript. The helper gets a console it does not show (`CREATE_NO_WINDOW`) rather than none at all: started `DETACHED_PROCESS`, PowerShell's console host stopped before the first statement, and the lane read a `restart.log` with the server's line and nothing from the helper. `supervised()` is therefore true on any Windows with PowerShell; until the helper existed the update button there ended in "stop it and start it again", which for a task-started server meant Task Scheduler.

## The gate every request passes

Three middleware, and the order is load-bearing. Starlette builds the stack with the last one added on the outside, so `security_headers` is declared after `authenticate` and therefore wraps it. That matters because `authenticate` returns some responses without ever calling a route, and those refusals need the headers too. The sign-in page is one of them: it is the page an unauthenticated visitor actually sees and it takes a password. `wait_for_closing` is declared before both and so sits inside them: a request to a project whose session is closing waits there for the close to finish, and a request that has not been authorised must never be able to wait on anything.

`authenticate` does three things in order.

**Origin.** `Sec-Fetch-Site` when it is sent, `Origin` against `Host` otherwise, and absence is allowed. A page in a browser cannot arrange to send neither, and curl, the installer and the test client send neither. This exists because `SameSite=Lax` does not separate ports: a page on `http://127.0.0.1:5173` is same-site with NextTex and its cookie travels.

**Size.** A `Content-Length` past the limit is refused before the body is read. Starlette spools a multipart body to a temporary file before any route is called, so without this the per-file limits would bound what lands in a project and nothing would bound what the machine absorbs. A chunked request sends no length and slips past, which is why the per-file limits exist as well rather than instead.

**Credentials.** Two of them, doing different jobs. The instance token is what the installer prints: the recovery path, and how a script gets in. A session is what a browser holds, minted when it proves it knows the password or arrives carrying the token. They are separate so that a copied cookie is not a copied install, and so one browser can be signed out.

WebSockets do not run HTTP middleware, so `authorise_socket` applies the same origin and credential rules at the socket route.

An unhandled exception is answered by a handler that logs the route with a short reference and returns that same reference to the browser in the shape the client's single error path reads. Starlette's own answer is the plain text "Internal Server Error", which is not JSON, so the browser could not read it and fell back to the status line.

## Projects and sessions

A project is any directory of LaTeX. NextTex does not own it, move it, or require a layout. It adds two things: an optional `nexttex.toml` at the root, which you may commit, and a `.nexttex/` directory of generated state, which you should not.

**There is no main document.** Every `.tex` with a `\documentclass` and a `\begin{document}` of its own that nothing else reads is a document, with its own `DocumentState` in the session: its own `ProjectPaths`, `CompileScheduler`, build counter, diagnostics and PDF under its own jobname. `nexttex/deps.py` holds the graph. `standalone_candidates` lists the documents not yet on the preview strip; `owners` says which documents a saved file belongs to, so a save rebuilds only those; and `root_of` climbs the other way, from a file through everything that `\input`s, `\include`s, `\subfile`s or `\import`s it to the file nobody reads, so a chapter three parts deep previews the thesis. Where two documents read one file, the document on screen wins, then one already on the strip, then the first by path, so the page never changes under the writer and the answer is the same on every open. Which documents are on the strip is viewer state: `.nexttex/previews.json`, per install, read by `PreviewList` in `nexttex/project.py`, because `nexttex.toml` is shared with collaborators and a preview that follows one writer's editor must not grow the strip on another's screen. A toml that still carries `main` and `previews` from an older NextTex is read once to seed that list and the keys are not written back. A project with no document at all opens with an empty strip; the routes that once meant "the main document" mean the document in front, and answer 404 rather than 500 when there is none. `POST /api/projects/{id}/previews` takes any `.tex` path and answers with the document it belongs to, registering it if it was not on the strip, which is how the editor's active tab pulls its document forward. The two strips also close together, and that is the browser's affair with nothing new on the wire: when a document is taken off the strip, `orphanedBy` in `frontend/src/tabs.ts` inverts the `owners` map the browser already holds, as it stood before the removal, to find the open files that belonged to it and to nothing still on the strip, and `closeMany` in `frontend/src/App.tsx` moves both strips in one store write so the follow effect never sees them disagree. The other direction is narrower: `App.tsx` keeps a per-window `followed` set of the documents this window put on the strip by following an opened file, and `unfollowed` drops such a document when its last open file closes, never the last document on the strip and never one the writer selected, added or acted on by name. The set is the window's own, in its `sessionStorage` under the project's id, so it survives that window's reload and is never shared, because the strip is shared between windows and the tabs are not.

**The strip follows the files it names.** Nothing did this for a long time: a previewed `main.tex` renamed to `thesis.tex` left `session.documents` keyed by a path that no longer existed, with a scheduler that would build a missing file, `previews.json` naming the old path and the tab wearing the old name until the next open quietly dropped it; a deleted document stayed registered and its stale PDF went on being served. `ProjectSession.reconcile_documents` is the one method now, and every path a change can arrive by reaches it. The rename route names what moved and the delete route what went; a peer's rename lands through the collaboration store, which cannot await, so `note_moved` spawns the same sequence; and an outside `mv`, an `rm`, a `git checkout` or the agent's own shell reach the session only as the watcher's `files_changed`, whose debounced re-scan checks every registered document against the disk before publishing. A moved document, or one under a moved folder, is retired, taken out of the registry before the new name goes in (the jobname check would otherwise collide a same-stem move with itself), re-registered at the same place on the strip, kept visible if it was, and given a build so its page comes back without a keystroke. A gone one leaves; the "last document stays" refusal belongs to the writer's own close gesture and does not apply, so a strip whose only document was deleted becomes empty and the pane says so rather than offering a template to a project that has content. A move whose new name would build to the same PDF as another document cannot be registered, so it leaves and `previews_changed` carries a `notice` saying why. A restored `.tex` that `root_of` says is its own root goes back on the strip; a restored chapter needs nothing. The `previews_changed` for a rename carries a `renamed` map, and the browser's store moves its tabs, `activePath`, the version being viewed, the strip, the build dots and the diagnostics in one write when it reads it, through `renamePaths` in `frontend/src/tabs.ts`; the route publishes that event before its own `renamed`, because the effect that makes the page follow the file runs when either strip changes and, with the strip moved while the tab still said `main.tex`, it asked the server to preview a file that no longer existed.

The `Registry` is the list of projects, a JSON file in the state directory. A project's id is derived from its path, which is why relocating a project gives it a new id and is implemented as a removal and an addition that keeps its place in the list. An entry carries a `state`, `active`, `archived` or `trashed`, and `state_at`; a registry written before the states reads as all active. `Registry.set_state` writes it, `POST /api/projects/{id}/state` sets it (404 for an unknown project, 400 for a word that is not one of the three; trashing closes a live session the way forgetting does), the open route makes an opened project active, and `DELETE /api/projects/{id}` is what "Delete" in the trash and "Empty the trash" call, one project at a time. `visibleProjects` in `frontend/src/project-filter.ts` takes the view, so the find field and the sort work inside whichever list is showing.

`session_for(project_id)` returns the `ProjectSession`, building it if the project is not open. "Open" is a thing a person does to a window, not a precondition the server keeps: while it was one, restarting the server made every route a tab was using answer 404, including its event stream, which then retried forever with nothing on screen to say so.

A session owns what must not be duplicated: the compile scheduler that serialises builds, the agent holding a Claude session, the CRDT store, and the fan-out to browser tabs. It is evicted after thirty minutes of nobody asking for it, unless something is relying on it: a browser holding the event stream, a browser holding an editing socket, an agent turn in flight, or a shared project, which counts whether or not a collaborator is connected this second, because closing the peer network is what takes the project off the network.

Eviction is safe because a session can always be rebuilt from disk. It is never about losing state, only about what would be interrupted.

**A session being closed cannot be replaced halfway.** `close()` awaits, so between popping a session from the table and finishing with it there was a window in which any request built a fresh session over the same project, and the two flushed the same documents to the same files from two sets of state. `_close_session` keeps the project id in `CLOSING` for the whole of the close, with an event that is set when it is over, and `session_for` refuses an id that is in there. A request arriving in that window is not refused straight away: the `wait_for_closing` middleware waits on the event for up to `CLOSE_WAIT_SECONDS`, three seconds, and only a close that outlasts that is answered with the 503 and "try again in a moment". A close is a flush and a few socket closes, so the wait is nearly always a few milliseconds, and the ceiling is there so a close stuck on a disk cannot hold every request to the project for ever. The document socket does the same wait itself, since the HTTP middleware does not see the websocket scope; until it did, a browser reconnecting its document during a close was handed the session whose documents were being flushed. Two closes of one project can overlap, the reaper's and a provider change's, and the second reuses the first's event rather than replacing it, because a replaced event is never set.

**There are no subagents, and the question this paragraph used to ask is settled.** It asked whether `PreToolUse` fires for the tool calls a subagent makes, said the test suite could not observe it, and said the way to settle it was a live run with a real account. The answer was in the installed SDK the whole time, in the `.venv` this checkout has always had. `PreToolUseHookInput` inherits `_SubagentContextMixin`, whose docstring says `agent_id` is present only when the hook fires from inside a spawned subagent and absent on the main thread, so the hook does fire there; and `ClaudeAgentOptions.forward_subagent_text` says a subagent's `tool_use` and `tool_result` blocks are already emitted as ordinary messages carrying the id of the call that spawned them. It was recorded as needing an account and a turn when it needed a grep, which is the more useful half of the lesson: the dependency you vendored is a primary source, and reading it is cheaper than any experiment.

The fence was therefore never reachable around, and subagents are refused anyway, for a different and simpler reason. A subagent's work reaches the panel as one line saying a subagent ran. The panel is supposed to be the account of what was done to somebody's manuscript, and work nobody can watch is work nobody can correct. Three layers, because the tool's name belongs to the CLI rather than to this code: the fence refuses `Task` and `Agent` as the *first* statement in `_decide`, before anything that could allow them, since the last branch there allows a tool name it has never heard of when the writer has asked for no cards; `disallowed_tools` removes both from the model's context so it is not offered a thing it would then be refused; and any call arriving with an `agent_id`, or any message arriving with a `parent_tool_use_id`, is refused whatever it is and ends the turn with a notice, which depends on no name at all. That last one should be unreachable, and it exists so that a change in the CLI cannot make the first two quietly untrue.

**A project from somewhere else arrives through `POST /api/projects/arrive`**, which takes a folder, and either a zip in the multipart body or an arXiv id or a git URL in `source`; `nexttex/arrive.py` is the mechanism. The folder must be absent or empty, the rule `create_project` already applies, and on any failure it is removed again so the next try finds it as it was. An archive is the same channel as an upload and gets the same fence: an entry with an absolute name or a `..` segment, a symlink or a hard link, and every `is_control_path` entry (`.git`, `.claude`, `.nexttex`, `latexmkrc`, `Makefile`, `.envrc`) is left out and named in the answer's `skipped`, so a zip that carries a `.claude/settings.json` arrives without it and the writer is told in a notice; a single top-level folder is stripped; the entry count and the written bytes are capped, and the bytes are counted while writing because a header can lie. `fetch_arxiv` asks `arxiv.org/e-print/<id>` with NextTex's user agent, a timeout and a size cap, and `unpack_arxiv` reads what came back as a gzipped tar, a gzipped single file that becomes `<id>.tex`, or a PDF-only submission, which is refused with a sentence; the gzip is inflated in chunks against the same budget. `NEXTTEX_ARXIV_BASE` replaces the host so the browser tier serves the archive itself. `gitrepo.clone` runs `git -c protocol.file.allow=never clone -- <url> .` in the folder through `_run`'s prompt-free environment with `CLONE_TIMEOUT`, and the route holds the URL to `https`, `http`, `ssh`, `git` and `user@host:` first, so `file://`, a bare path and `ext::` never reach it. A clone brings `.git` by necessity, the one control directory this way in accepts; the reasoning above `CONTROL_DIRS` in `project.py` about a cloned folder being somebody else's is what covers it. The fetch, the unpack and the clone run off the loop, and the folder is then registered as any added folder is.

**One constraint worth knowing before you touch this.** A session's CRDT objects are bound to the thread that created them. pycrdt panics outright, not raises, if one is used from another thread. That is why the reaper is a task on the event loop rather than a thread, and why a test that closes a session has to do it on the app's own loop. The drop counts as a use: an object the garbage collector frees on another thread is reported as an uncatchable exception, which pytest turns into a warning filed under whichever test it ran in. The suite carried one of those for a long time, and its source was in the store, not in a test. `CollabStore.close` ended each subscription with `subscription.drop()`, and pycrdt's `Doc` keeps every subscription in a list of its own, so the dropped object stayed alive inside the document; the document sits in a reference cycle, since the callback pycrdt wraps around ours holds it, so only the cyclic collector ever freed it, on whichever thread that ran on. `close` calls `doc.unobserve(subscription)` now, which takes it out of the document's list too, on the closing thread. Two smaller holes were shut on the way: `ProjectSession.close` cancels the re-scan the watcher arms 0.3 s after a file lands, which could fire into a closed store, and `CollabStore.body` opens nothing once closed. The route tests close every session on the loop that built it (`tests/api/conftest.py`), and `tests/conftest.py` makes that warning an error so the next one cannot hide.

## The document model

This is the part that is not obvious, and everything about saving depends on it.

**Every text file in a project is a CRDT document, and the file on disk is a projection of it.** Not the other way round. Every project is backed this way, shared or not, so there is one code path rather than two.

The alternative NextTex used to have was a hash on every save: the browser sent what it last agreed the file said, and a save whose hash had moved on was rejected. That is right when the two writers are one person in two stale tabs, and wrong when they are two people, both right, both typing.

The layout is **one document per text file, plus a manifest listing them**. One document for the whole project is the obvious choice and the wrong one: a two megabyte thesis with a year of tombstones behind it would be a multi-megabyte download every time it opened, and a browser needs the file it has open, not all forty.

Three paths move text.

**Browser to document.** A `y-codemirror.next` binding over a WebSocket per open document. The server applies the update to its copy and fans the result out to everyone else with that document open. The binding is a view plugin, so it watches its `Y.Text` only while its `EditorState` is the one in the view; a tab that is not in front keeps its state parked, with its undo history and caret, and the shared text moves on without it. `frontend/src/panes/parked.ts` folds the shared text into the parked state as it comes back, as one minimal change so the caret moves with the text, and everything that reads a parked file's text reads the shared text rather than the state. Without that an outside rewrite, an agent edit or a collaborator's typing in an open-but-not-in-front file was invisible when the tab came back and the next remote change was spliced into the wrong offsets. A deletion closes its tabs: the delete route's `files_changed` and the one `ProjectSession.note_trashed` publishes carry `gone`, the paths that went, the way the rename route's event carries `renamed`; the watcher's road says it from `CollabStore._settle_gone`, where a record is flagged trashed once the file has stayed missing through the debounce that tells a deletion from an unlink-and-recreate rewrite, so a tab does not close for a file that is back a moment later. The browser closes every tab at or under a gone path through `closeMany`, the same road as the strip's close button, and the tree's own delete closes them directly as well so the window that deleted does not wait for the event. Awareness messages, who is where and what they have selected, are relayed and also parsed and kept, because a browser that goes away has to be reported at once. The browser writes its own position (`ProjectCollab.here`, the file and the line) on every caret move, from `Editor.tsx`'s cursor handler before that handler's early return for a short selection; it once sat after it, so a collaborator who only read or moved their caret was "not in a file" to everyone until they typed. y-protocols only drops a silent peer after thirty seconds and that timeout is a module constant, so a collaborator who shut their laptop sat in the margin for half a minute, which is worse than not showing them, because a caret means somebody is there.

**Document to disk.** A change marks the document dirty and schedules a flush 120 milliseconds later. The flush materialises the text, compares it against what was last written, resolves the path, writes atomically, records a version, notes the edit and schedules a compile. A file that could not be written stays dirty and is retried; a file that was *refused* does not, because a record naming `.git/hooks/pre-commit` will name it just as much next time.

**The gap before the watcher.** `adopt()` runs when a session opens and the watcher reports only what happens once it is watching, and a project opened into an idle watcher waited up to a second for it, so a file written in that second was never adopted until the project was next opened; the first cross-machine check lost a `notes.tex` that way. The idle watcher now waits on `WATCH_WAKE`, which `_restart_watch` sets, and `_adopt_what_appeared` runs every open session's `adopt()` just before `awatch` starts. Adopting was the whole of it until the backlog run, and a file the manifest knew was left alone, so an edit saved from another editor in that second under a document that was already open reached neither the document nor the history, and the next keystroke in the browser wrote the document over it. What appeared and what changed under an open document now go to `_fold_tick` together, as the tick the watcher would have reported, and the browsers are told with the same `files_changed`. "Changed" is measured against what the store last projected to the file, not against the document: the document is ahead of the disk by the debounce whenever somebody is typing, and the disk then holds NextTex's own last write, which is nothing to fold and would otherwise have begun a never-versioned file's history under the outside label.

**Disk to document, after a stop.** The watcher reports only what happens while the server is up, and a document with a log is opened from the log, so a file edited in another editor while NextTex was stopped was overwritten by the next projection without a version. "Disk differs from document" cannot be the test, because the log is appended inside the transaction and the file written up to 120 ms later: a server killed in that gap reopens with the document ahead of the file, and folding the file in would publish a revert to every peer. So the store keeps `projected.json` beside the docs, file id to the sha256 of what it last wrote, saved once per flush, and `_fold_outside_edit` runs when a document with a log is opened: a file matching the record is untouched, and if the document has moved on it is written out now rather than at the next edit; a file matching the document brings the record up to date; anything else is an outside edit, ingested and recorded as a version by this install with the note "changed while NextTex was not running", or with the watcher tick's own label and stamp when the document is being opened inside one (`live_outside_edits`, below). A file with no record keeps the old rule, the document wins. `send_documents` opens every text document when a link comes up, so on a shared project this runs for every file at the first connection; on a private one, when the editor opens the file.

**A join holds its documents in memory until it is accepted.** `POST /api/collab/join` syncs the project, waits for the bodies rather than for the manifest that lists them, and answers with the file list. Nothing is written: the store and the peer connection stay open in `PENDING_JOINS`, and accepting marks every record for projection and flushes, while discarding closes both and removes the folder, which by then contains only `.nexttex/collab`.

**A path from the other end is fenced at both ends of every operation it names.** `resolve_for_write` is the fence, and a rename has two paths, not one. While only the target was resolved, a peer could name a file `../../.ssh/id_rsa`, let that become the baseline `settle_paths` measures the next change against, then rename it to `notes.tex`: the source was built as `root / was` with no fence, so the file was moved off the disk into the project, where the manifest handed it to everybody in the share. The baseline is fenced when it is recorded and the source is fenced when it is used. A local file the rename displaces goes to the trash rather than being renamed out of the way in silence.

**Disk to document.** `ingest` folds an outside change back in: a `git pull`, the agent's own write, an editor in another terminal. It diffs against what was last projected and applies only the spans that moved, so a remote cursor is not thrown across the document by an append. The spans `edits_for` makes are in Python's code points and pycrdt indexes a `Text` in UTF-8 bytes (yrs's default offset kind; `TEXT_UNIT` asks the library once at import with a probe rather than assuming), so `splice` converts each span's offsets against the text it was computed on before touching the document, with a fast path for ASCII. Before that conversion every splice after an accented letter landed early by the number of extra bytes before it, and a bibliography full of `Martínez` came to read `@articløidstrup2014improved` on screen while the file on disk was clean; `tests/properties/test_collab.py` now draws its prose from an alphabet with one-, two- and four-byte characters, and applies the store's own `splice`. Behind that, a guard: after the splice `ingest` compares the document with the text it was told about and, if they differ, logs an error naming the file and puts the file in whole, so whatever a diff gets wrong the document a fold leaves behind is the file, and the next keystroke cannot write a garbled document over a clean one.

**And into the history, since the backlog run.** The projection's own writes were versions and an edit made while the server was stopped was one, and an edit the watcher saw was not: a `git pull` reached the document through `ingest` and nothing recorded what the file held before or after. `_fold_tick` in `server/main.py` is one tick's work. It enters `CollabStore.live_outside_edits` with a stamp, `outside:<ms>`, which sets the label and `source` the store's own fold records under for the length of the tick; asks `body()` for each touched document first, so that a document not yet open is opened there and its fold, if it has one, records inside the same stamp; ingests; and then records a version for every file that changed, off the loop, `by="you"`, "changed outside NextTex", with the document's text before the fold as `previous` so the first sight of a file seeds its earlier state. A document that was not open and had no log is seeded from the file as it now is, so its earlier state was never anywhere NextTex could see and the new state is recorded as a creation; the same holds for a document the browser's socket opened in the moment between the write and the tick, which the tick meets as open with nothing to fold, so a file `ingest` left alone is still recorded when it has no history yet, and left alone when it has one, since that is a rewrite to what it already said. Every file one tick touched shares the stamp as its `source`, which is what keeps an outside version from coalescing with a typed save: the history's burst rule keys on `source`, and treats every `outside:` stamp as one class among themselves, so a vim user saving every ten seconds gets one version per ninety-second window like typing does, under the latest tick's stamp. The timeline the whole-project list reads, `History.timeline`, folds the versions of one stamp into one row carrying `paths` and `count`, before its limit is applied so a pull cannot fill the list with its own files. A text file the watcher sees go gets a `delete` version at the flush that flags it, `_record_outside_deletion`, with the document's text; `_gone_pending` carries the stamp of the sighting, and the adopt walk's sightings, which are files that went while nothing was running, carry none and record nothing, since their last state is not known here.

An edit reaching the disk measures at 3.1 ms on a thesis-shaped project, of which the edit arriving is 3.0.

**Undo belongs to the document, not to the editor.** A live editor's Ctrl+Z runs the scoped `Y.UndoManager` that `collab.ts` builds per file, bound by `yUndoManagerKeymap`; CodeMirror's own `history()` is not in a live editor's extensions at all. The two cannot both be there. A buffer is built before its socket has synced, so the file arrives afterwards as one transaction, and an editor with CodeMirror's history had that transaction on its stack: six presses of undo emptied the file on disk and for every other browser. The read-only panes, a version being viewed and a file that could not be connected, keep CodeMirror's history, because they have no shared document to own theirs. A chosen keymap keeps the same owner. `keymapCompartment` in `editor-setup.ts` is empty until the writer picks Vim or Emacs on the settings sheet, and then `Editor.tsx` fetches `frontend/src/panes/keymaps.ts`, a chunk of its own, and reconfigures it; both packages bind their undo to CodeMirror's `undo` command, which with no `history()` in the state is a dead key, so `keymaps.ts` rebinds Vim's `u` and `<C-r>` through `Vim.defineAction` and the four spellings of Emacs's undo and redo through `EmacsHandler.bindKey` to the commands `yUndoManagerKeymap` runs, which are the document's. The Emacs keymap is `frontend/src/vendor/codemirror-emacs.js`, the package's ESM build vendored with two lines changed: it installs its keys and its commands at module load through calls its own bundler marked pure, and a production build dropped both as dead code, so the app as built had an Emacs mode with no keys in it while vitest, on the unminified source, had them all; the CommonJS build carries no annotation but importing it brings a second copy of CodeMirror. The file's header says so and carries the licence. `editor-undo.test.ts` presses each keymap's undo on a document that arrived from the socket and finds only what this keyboard typed undone, with `historyField` still absent.

**Copying a file is a fourth path, and it has to start by closing the second one.** `POST /api/projects/{id}/file/duplicate` flushes every dirty shared document before it copies anything, because the file on disk trails the document by the 120 millisecond debounce and a copy taken without that would hold the chapter as it was rather than as it is, with nothing on screen to say which of the two the writer had got. The name is chosen on the server by `unique_name`, the same rule the trash restores through and the upload chooser quotes back, and the route answers with the name it picked rather than accepting one. It publishes its own `files_changed`; the watcher would find the new file eventually and in a batch, so this is what makes the copy appear in the same beat the menu item was clicked in, for every tab and every collaborator. A folder goes through the same route since the backlog run: `shutil.copytree` off the loop, with symlinks, the ignored directories, NextTex's own files and the scratch suffixes of a write in flight left out by `_copy_tree_skips`, because a link copied as a link still points where it pointed, which may be outside the project. Each text file in the copy is given a first version, `create`, naming the file it came from, recorded in the same thread as the copy rather than on the loop once per file; the copies are not marked as the session's own writes, since `copy2` keeps their mtimes and the watcher's adoption is what puts them in the manifest. The root itself is refused. `unique_name` treats a folder's name as whole, and the trash's restore tells it the kind, because the path in the way may be a file where a folder is coming back.

**Deleting one publishes `files_changed` too**, structural and naming the path, beside the `trash_changed` the trash panel reads: until it did, the other windows kept the row and the document re-scan never ran, so the strip's `+` went on offering a document that was in the trash until the watcher caught up.

**Creating a file is the same shape.** `POST /api/projects/{id}/file/new` touches the file and then ingests it into the manifest itself, before it answers. The browser opens a file it just made the moment the route returns, and `waitForFile` in `collab.ts` gives it eight seconds to appear in the manifest before falling back to a read-only pane and a toast about reloading. The manifest used to learn of the file only from the watcher, whose poll, debounce and socket round trip were exceeding that on a loaded machine; a Playwright spec that types into a new file was flaky for exactly this reason. The watcher's own ingest, when it comes, diffs and finds nothing to do.

## Compiling

Every subscriber is told the state before it is told the news. The event
stream's first frame is `compile_state`, which carries, per document, whether
a build is running, which build, and whether one has ever finished.
`compile_start` and `compile_done` are published to whoever is subscribed at
that instant and are not kept, so without this a tab that opened a project and
built in the same breath missed its own build, and a stream that dropped
mid-build came back with nothing in the world able to lower the flag it had
raised.


A compile runs every time typing pauses, so the budget is about a second. Three decisions get it there.

**Only rebuild what changed.** A document using `\include` can be compiled one chapter at a time with `\includeonly`, which halves the work on a seven-chapter dissertation. Whether that applies is detected from the source, never assumed.

**Only run the bibliography when citations changed.** bibtex or biber, whichever the document asks for, and latexmk's reruns after it dominate a full build, and reference resolution matters when the bibliography moves, not on every keystroke. So an edit that changes the set of citation keys or labels, touches a `.bib` or the preamble, earns the next build a full pass, and everything else gets one pdflatex. The log has the last word: after a fast pass, `CompileScheduler._note_unresolved` compares the citation and reference keys the log left undefined with the set left undefined by the last full pass, and a difference earns a full pass too, as does the engine asking for bibtex to be rerun. A difference rather than a presence, because a genuinely misspelled key survives every full pass and would otherwise turn every keystroke into a latexmk run. The parsed log carries the undefined keys, the overfull count and the page count, and the agent's `compile` tool reports those rather than "built cleanly", which is what it said while every citation in the PDF was a question mark.

**And let the preview settle.** A fast pass is one engine run, and one run typesets against the last run's `.aux`, `.bbl` and `.out`: wherever an edit changed what a reference, a citation or a page number says, that run's page flow, and with it where the `[h]` and `[htbp]` floats land, is one pass behind. The engine says so in its log, "Label(s) may have changed. Rerun", "Rerun to get cross-references right", "Some pages have been shifted", rerunfilecheck's "has changed", and for a year those lines were suppressed from the gutter and read by nothing, while the full pass `_note_unresolved` asked for waited for a build nobody triggered; a writer saw figures on the wrong page until Rebuild everything. `latexlog.ParsedLog.rerun_needed` keeps the hint as a flag (`rerunNeeded` in the payload) beside `bibliography_stale`, `CompileScheduler.needs_full` says what the log's last word was, and `ProjectSession.compile` follows a fast pass that finished without error, was not superseded and left either flag up with one settling build, `force_full=True`, spawned after the fast result has gone out so the preview shows the fast pass at once and the settled layout a moment later. The settling build takes the same cancel and queue as any other, so a keystroke supersedes it; its events carry `settling: true`; and it never spawns a second, so a package that asks for a rerun on every pass cannot loop. An edit to the main file itself always takes the full pass (`note_edit`), so the fast path, and the settling, is what a chapter or an `\input` file gets; `e2e/specs/settling.spec.ts` types `\newpage` into an input file whose text names the page a later section is on and reads the page number back out of the PDF.

**The PDF route reads the file whole, measures it twice and looks for the trailer.** The engine writes the PDF in place in the build directory, truncating the same inode, so a `FileResponse` that set `Content-Length` from a stat and then streamed the file could be overtaken by a build and end short, which Starlette raises on as `Response content shorter than Content-Length` and the browser sees as a failed fetch over a document that was fine. `_whole_pdf` reads the bytes off the loop between two stats; a file whose mtime or size moved in between is being written now. A build between pages moves nothing, since pdfTeX ships pages out in bursts and idles while the next one typesets, so the bytes are also required to end in the `%%EOF` the engine writes last, which no half-written file has. Either way the answer is a 503 with `Retry-After` rather than a fragment, which the pane reads as a build in flight and keeps the page it has; the browser fetches again on that build's `compile_done` regardless. The download route's PDF goes through the same helper, because a build the writer's typing started a moment after the download decided the file was fresh rewrites the same inode, and a download that ends short is the copy that leaves the machine. A thesis is tens of megabytes at most and the route runs once per build, so the whole file in memory for the length of one response is the cheaper certainty; the snapshot copy that would let it stream again is more moving parts for a saving nobody would measure.

**Every download is fetched by the page, not handed to the browser as a link.** `GET /api/projects/{id}/download` serves one file, a folder or the whole project as an attachment; the ZIP walks the project on a thread into a temporary archive and serves it with a `FileResponse`, skipping the build directory, `.git`, `.nexttex`, NextTex's own files and the `.nexttex-tmp` scratch file an atomic write leaves beside its target for a moment, and a file that is listed and gone by the time it is read is left out with a warning rather than failing the archive, since an open project is written under the walk every 120 ms. In the browser `download` in `frontend/src/chrome.tsx` fetches the URL and saves the blob under the name `Content-Disposition` gives, and the tree's row menu, the source tab's, the image viewer, the history panel and the viewing banner all go through it; `downloadZip` and `downloadPdf` are the same road with their own sentence. They were `<a download>` links, and from inside an open project over the tailnet's HTTPS address the browser cancelled such a download before sending a byte once the page had been open about ten seconds, the ZIP, a single file and a PDF alike, reproducibly, in Chromium against this code, with nothing in the server log; a `fetch` of the same URL from the same page at the same moment succeeded, and over plain HTTP the link never failed. Why Chrome's download manager refuses a navigation-mode request there and the page's fetch does not was not established; the fetch road is what works, and it also turns a 500 or a 503 into a sentence rather than a file named `download`.

**Word, HTML and Markdown come from pandoc, through the same download route.** `format=docx`, `html` or `md` on `GET /api/projects/{id}/download` names the document the way the PDF branch does, the one on the strip or any `.tex` that can build on its own, and `nexttex/export.py` runs pandoc in the document's own directory with the root on the resource path, `-f latex` to `docx`, `html` or `gfm`, `--standalone --embed-resources` for HTML so the page travels with its images inside it, and `--citeproc` with every `.bib` the project walk finds, into a temporary directory whose file is answered whole with the attachment disposition `chrome.download` reads the name from. pandoc is an optional tool the way `pdftotext` is: `nexttex/tools.py` and the installer's survey name it and NextTex never installs it; `export.pandoc_here` is `NEXTTEX_PANDOC` or the one on PATH, the seam `NEXTTEX_TLMGR` is for `tlmgr`, which is how `tests/fake_pandoc.py` stands in for it under the browser tier; without it the route answers 409, pandoc's own last line of stderr is a 422, and `GET /api/tools` says whether it is here so the menu draws the three rows or nothing.

**The engine is chosen per document.** `compile.engine_for` reads a `% !TeX program = xelatex` line (or `TS-program`, TeXShop's spelling) from the first twenty lines of the real main file, never the stand-in, then the project's `engine` key in `nexttex.toml`, then falls back to pdflatex; a name outside `compile.ENGINES` is ignored rather than refused, since a config must never make a project unopenable and the value may have come from an editor with more engines than this one. The scheduler asks for the project's setting through a callable at each build, so a change on the settings card reaches the next build and not the next restart, and a build whose engine differs from the last one's is made full, because the `.aux` files in the build directory were written by the other engine. `fast_argv` swaps the binary; `full_argv` maps the engine to latexmk's mode switch and command option, `-pdf`/`-pdflatex=`, `-pdfxe`/`-pdfxelatex=` and `-pdflua`/`-pdflualatex=`, with the same inner flags for all three, since every engine accepts `-synctex=1 -interaction=nonstopmode -file-line-error`. The log parser, synctex and the `.aux` files are the same for all three, so nothing downstream knows which ran; `CompileResult.engine` carries the name for the result payload, and a `NO_ENGINE` result names the engine that was missing so the status strip can say "xelatex is not installed" rather than "the build did not run".

**Never let two runs share a build directory.** A new keystroke kills the run in flight before starting the next, and it kills the whole process group, because latexmk spawns children that outlive it.

**The engine runs in the document's own directory.** Every document was compiled from the project root, so one at `papers/a/paper.tex` had its `\input`, its `\graphicspath` and a style file beside it resolved against the root, silently, and a root copy of a style shadowed the local one. `ProjectPaths.workdir` is the document's directory now and the engine runs there, which is what running it by hand does; `TEXINPUTS`, `BIBINPUTS` and `BSTINPUTS` name that directory and then the root, with the trailing separator that keeps the installation's own search path, so a root-relative path that resolved before still resolves. Two consumers of the engine's paths follow it. The log parser takes the working directory as the base for a relative path, falling back to the root for a log an older build wrote; and both synctex queries run there and resolve the same way. In practice nearly every path arrives absolute, because kpathsea reports a file by the search-path entry it found it under and both entries are absolute. `latexmk -cd` is not used: it would move the output directory along with the working one, and the output directory has to stay the project's one `build_dir`, where every document's jobname keeps its files apart.

The one non-obvious mechanism is the **stand-in main file**. `\includeonly` has to sit in the preamble, so scoping a build means either editing your main file on every keystroke or compiling something else. Editing yours is not acceptable, so NextTex writes a shadow main file beside the real one and compiles that. The stand-in has one line the real file does not, when the real file had no `\includeonly` of its own to replace: the directive goes on a line of its own after `\documentclass`, and everything below it is one line further down in the copy. SyncTeX only ever saw the copy, so `nexttex/synctex.py` keeps `shadow_shift`, which finds that line by comparing the two files rather than by remembering what the last build did, and both routes correct for it: `/api/projects/{id}/synctex/inverse` moves a line the map reports for the stand-in one up, and `/api/projects/{id}/synctex/forward` asks about the real file first and, when the map does not know it, about the stand-in with the line moved one down.

**The Markdown pane has no inverse search route, and needs none.** `parseBlocks` in `frontend/src/panes/prose.tsx`, the chat's own parser, keeps the 1-based source line every block starts on and one per list item; `frontend/src/panes/Markdown.tsx` writes them into the DOM as `data-line`, and a double-click finds the nearest one, reads the word the second click selected, and asks `lineOf` in `frontend/src/panes/markdown-source.ts` which of the block's own lines the word is on. What reaches the editor is the same `openFile(path, line, hint)` the page's double-click uses, with the hint marked `plain` so `locateWord` blanks no `%` comment and no `\cite{...}` key out of a line of prose. The tab itself, chosen on the preview strip, opens its file through `openFile` too, the way a document tab does through `showPreview`.

Cancellation has an ordering subtlety worth keeping. `cancel` reads the process handle, and that handle is None for the whole of a build's setup: deciding the scope, writing the shadow, mirroring the build tree, spawning. A build arriving in that window used to cancel nothing and the older one ran to its two minute timeout holding the lock. The generation is therefore checked once more the moment the process exists, and once more after the process ends: latexmk traps the signal a superseding build sends and can exit with a code of its own after killing its engine mid-run, so a superseded full pass was reported as finished, cleared the mark that asked for a full pass, and left a torn `.aux` for the next fast pass to typeset against, which is how a fast pass right after a whole build found every citation undefined. A run whose generation moved while it ran is cancelled whatever code it left.

The engine's log is read and parsed off the loop. It is multi-megabyte on a thesis and the parser is regex heavy, and this runs after every build on the path that publishes to every subscriber.

`latexmk` is given `-norc`, because `./latexmkrc` is arbitrary Perl read from the working directory by a build the editor starts on its own.

`-shell-escape` is the same question with a different answer. minted and pythontex genuinely need it, so `nexttex.toml` may ask for it with `shell_escape = true`; the flag is passed only when this machine has said yes to this project, in `Settings.shell_escape_allowed`, a list of project ids in the install's own `config.json`, where a project cannot bring the answer along. `ProjectSession.shell_escape_state` folds the two into "off", "asked" or "on"; the scheduler asks for it at each build through a callable and passes the flag on "on", in both passes and inside latexmk's engine string as well as on latexmk's own line. `POST /api/projects/{id}/shell-escape` is the machine's answer, and it schedules a full build of every document, because the build the writer is looking at is the one that ran without the flag. That build carries `-g`: latexmk decides from its own database whether the sources changed and skips the engine when they did not, and the flag alone is not a change it notices, so the first build after Allow ran nothing. The need for `-g` outlives a build cancelled on the way, since Allow schedules one and a keystroke a moment later replaces it. `nexttex/texpkg.py` is the drawer's Install button. `explain.annotate` puts the style, class or definition file a "not found" names on the row as `missingFile`, only when it is a bare name a package manager could supply, never a path like a missing figure. `GET /api/projects/{id}/tex/package?file=` asks `tlmgr search --file --global /<file>` off the loop, with a timeout, and takes the first package whose path ends in the file under a tree a document reads from, `tex/latex/` before a documentation tree with the same basename; the answer is remembered per file, since the drawer re-renders on every build. `POST /api/projects/{id}/tex/install` runs `tlmgr install <package>` behind one lock, with the name validated against the same shape `plots.PACKAGE` uses so nothing option-shaped reaches the manager, returns the manager's own output on failure, and on success schedules a full build of every document. The binary is resolved rather than named, for the reason `install_tex_extras` records about `tlmgr.bat`, and `NEXTTEX_TLMGR` overrides it, which is how the browser tier points the server at `tests/fake_tlmgr.py`. MiKTeX's `mpm` is wired the same way with the file's stem as the package name and has not been run against a MiKTeX; the tracker says so.

Renaming a label, a citation key or a macro is `nexttex/rename.py`: `references_to` finds every use by the syntax, `\label` and the reference family with their comma lists for a label, the `@type{key,` line of a `.bib` and the cite family with their optional arguments for a key, the definition and every `\name` not followed by a letter for a macro, and marks a hit after an unescaped `%` as commented; `rename` rewrites those spans in reverse order per line and leaves the commented ones unless asked. `GET /api/projects/{id}/references` and `POST /api/projects/{id}/rename` read the same texts the project search reads, the open documents first, and the rename goes back through `_save_text`, so each changed file gets a version and the shared document is folded, and publishes `files_changed`. In the browser the tooltip on a `\label`, `\ref` or `\cite` carries *Find references* and *Rename*, F2 on one is the rename, and both set `symbolRequest` in the store; the search panel answers, listing the uses file by file with the commented ones marked and holding the rename box and the confirmation, and `App` opens the rail the way Mod-Shift-F does.

Folding is `frontend/src/folds.ts`: `foldRanges` walks the document text once per version for headings and `\begin`/`\end` pairs, skipping verbatim blocks, and a `foldService` answers per line from the map; the gutter, the placeholder and `foldKeymap` are CodeMirror's, and `foldEnclosing` on `Mod-Shift-[` walks up to the innermost range that reaches the caret. It is a view decoration on the state, so the shared document and the undo history know nothing of it.

Every label's number rides with the symbols. `nexttex/auxlabels.py` reads `\newlabel{name}{{number}{page}{caption}{anchor}{}}` out of each previewed document's `<jobname>.aux` and every file it `\@input`s, which is where an `\include`d chapter's labels are, mirrored under the build directory; the anchor's head, `figure`, `subsection`, `equation`, is the kind, cleveref's `name@cref` entries are skipped, and an `\@input` naming a path outside the build directory is not followed. The `/symbols` route merges `number`, `page` and `kind` into each label of the source scan's answer, reading the files on every ask rather than caching them, since they are small and change on every build and the editor asks once per build when `pdfStamp` moves. The hover on a `\ref` says "Figure 3, on page 7" from them, with the file and line beneath, and the completion list shows the same beside each label; before the first build there is only the place. The scan also says which environment each label sits in: `environment_index` in `nexttex/symbols.py` walks a file's `\begin` and `\end` edges once with a stack, and `environment_facts` gives a label its innermost figure, table or maths environment as `env`, with a figure's first `\includegraphics` path as `graphic`, a figure's or table's `\caption` as `caption`, a table's inner `tabular` (the environment included) or a maths environment's inner text as `body`, cut at 4000 characters with `bodyCut`; a section label carries none of these, and an unmatched `\begin` indexes what it can. A hover on `\includegraphics{figures/plot}` shows the figure itself, resolved against the image paths the scan collected with the suffix the call leaves off, through the thumbnail service the file tree's card uses (below).

The engine's version rides on every build. `compile.engine_version` runs `<engine> --version` once per engine per process, off the loop the first time, and keeps the first line, "pdfTeX 3.141592653-2.6-1.40.29 (TeX Live 2026)"; `CompileResult.engine_version` carries it, the `/log` route returns it beside the text with the engine that ran, the drawer prints it as the log's first line, and the installer's survey fills `Finding.version` for the TeX finding from the same `--version` so `report.tools_section` prints it in the bug report. A build that differs between two machines is explained by that line more often than by anything in the log.

`nexttex.toml` itself is re-read whenever a `files_changed` names it, by an edit in the editor or a change outside, and `project_changed` is published with the new values; it was read once at open before, so an `engine` or `shell_escape` typed into the file did nothing until the next restart.

The submission check is `nexttex/submit.py`, and it involves no model. `GET /api/projects/{id}/submit?document=` reads the document's last log and PDF and the project's texts, the open documents winning over the disk as the rename route reads them, and answers a report of findings in the drawer's row shape with `source: "submit"`, each carrying a `kind` and an `explain`; a document with no log yet is a 409, because an empty report reads as a clean one. The log gives undefined references and citations, overfull boxes over five points and a "not found", with their file and line. The sources give a label defined twice, a label nothing references, a `.bib` entry nothing cites unless a file says `\nocite{*}`, a `\today`, a `\todo` or a TODO in a comment, a run of three or more comment lines totalling two hundred characters, and, when the project's `blind` key is set, an `\author` that does not say anonymous, an affiliation, a `\thanks`, an email or an acknowledgements section. The label and citation uses come from `nexttex/usage.py`, which reads `rename`'s `REF_CALL` and `CITE_CALL` so the reference and cite families are written once; the `.bib` keys and their lines come from the vendored `verify_bib.parse_bib`, read-only. The PDF gives what a log cannot: `pdffonts` lists every font with an `emb` column, and a `no` is an error, a `Type 3` a warning; `pdfimages -list` lists every raster with its `x-ppi` and `y-ppi`, and one under 150 is a warning that carries the page. Both tables are read from their tokens, `pdffonts` from the right because a type reads `Type 1C` and `pdfimages` by its header because nothing in it holds a space. The page count is the log's, or `pdfinfo`'s, and `page_limit` in `nexttex.toml` makes an excess an error. A missing poppler tool is a single row saying which check did not run, and `GET /api/tools` answers which optional tools the machine has so the panel can say so before Check is pressed and the Download drawer (`frontend/src/panes/DownloadPanel.tsx`, one block per document from `previews` and `candidates`, chips through `chrome.tsx`'s fetch functions, waiting until the document's `builds` record has a PDF) can offer only what will work.

The bibliography check is `nexttex/bibcheck.py`, and it is the `.bib` case of the same `GET /api/projects/{id}/lint?path=` route that runs chktex over a `.tex`. It parses with the vendored `verify_bib.parse_bib`, read-only through `references._load`, because that is the one `.bib` reader here that carries an entry's line; the roadmap's claim that the field rules were already in that script was wrong, since it checks an entry against the publisher's record for its DOI, so `bibcheck.REQUIRED` is BibTeX's own table, new here, with a tuple where a type takes either of two fields. A key defined twice is a row at the second, a required field missing or empty is a row naming the field, a year that is not four digits is a row that quotes it, a DOI seen twice after lowercasing and stripping a `doi.org/` prefix is a row at the second, and an entry no document cites is an `info` row when `usage.cited_keys` over the project's `.tex` texts says what is cited, which it does not when a file says `\nocite{*}`. The route reads the `.bib` and the sources from the session, the open documents over the disk, because the editor asks again 800 ms after the last keystroke in a `.bib` and the flush is on its own debounce. `nexttex/texstyles.py` walks `bibtex/bst/` under the trees `kpsewhich --var-value` names for `TEXMFDIST`, `TEXMFLOCAL` and `TEXMFHOME`, once per process, and the `/symbols` payload carries the names as `styles`; without `kpsewhich` it is the four every BibTeX has. In the browser `frontend/src/panes/bib-complete.ts` is the completion source `languageFor` installs for a `.bib`: `@` at the start of a line offers the entry types as snippets with the key and the required fields as tab stops, a word at the start of a line inside an entry offers that type's fields, and its `ENTRY_TYPES` mirrors the Python table with a test on each side naming the other's types. `\bibliographystyle{` in a `.tex` completes from `symbols.styles`.

`page_limit` and `blind` are `ProjectConfig` fields written by `/settings` like the switches and carried on `project_changed`, in the project's own file rather than the browser because a co-author submitting from another machine needs the same answers. In the browser `frontend/src/panes/SubmitPanel.tsx` is a rail footer panel like the papers; a row with a file and a line jumps through `openFile`, a row with a page turns the PDF pane through `PdfHandle.goTo`, a row with neither opens to its explanation, and an open panel checks again when `pdfStamp` moves or either venue fact changes.

## Collaboration

A peer is an ed25519 keypair and nothing else. There is no account and nothing to sign in to: the public half is the identity, iroh authenticates it as part of the TLS handshake, and "is this peer allowed" reduces to "is this key in the list".

Everything above `transport.py` is bytes in and bytes out. `IrohTransport` is the real one, QUIC over TLS to a key, hole-punching across the open internet. `LoopbackTransport` is a pair of queues chosen by an environment variable, and it can do the two things a real network does that are hard to arrange on purpose: lose a connection, and hold messages until later.

The share record lives **inside the project**, at `.nexttex/collab/share.json`: the share id, the members, and when this peer joined. It has to be readable before the document has synced, because it is what says whether a project is shared at all and it is the gate an inbound connection is checked against.

The identity lives in the **install's** state directory. Those two facts together mean a project folder copied to another machine is a stranger to its own share: the record travels and the identity does not. The app detects that and says so, because otherwise every member reports as not connected and the honest reading of that is that nobody is here.

**Joining is two steps and the first writes nothing.** Accepting an invite is downloading somebody else's files. The join syncs the project into memory, holds the connection open, and answers with the manifest: every path, its kind and its size. Accept writes them and registers the project; discard closes the connection and removes the folder, which really does leave nothing behind. A file the build would run is listed as offered and marked as one that will not be written, because what somebody tried to send is the more interesting of the two facts.

**Rejoining needs no invite.** An install whose project folder is gone is still a member: the identity lives in the install, not in the folder, and every member's gate admits a member's key on its own. `POST /api/collab/rejoin` reads the share card, refuses a share this install was removed from before dialling anybody, and `PeerNetwork.rejoin` takes the share id and the member list from the card, starts the transport and dials every member with a `HELLO` carrying no secret. From there it is the ordinary held join, `_hold_join`, shared with the invite route: the project arrives into memory, the offer card lists it, and accepting writes it. Accepting a rejoin also points the card at the new folder, which it did not touch until then so that a discarded rejoin leaves the card as it was, and takes the place of the registry's entry for the old folder rather than adding a second row beside a missing one. Accepting either kind opens the project, so its peers reach it at once rather than when somebody next opens it.

**A join or a rejoin may land in a folder that already has files.** Two documents built independently from identical text merge into both copies, every line twice, and nothing raises, so the rule used to be an empty folder or nothing. The rule now is ordering. Into a folder with files the store is built with `seed_from_disk` off and `holding` on: no document is built from the disk, nothing is written to it, and the logs the sync appends are what a discard removes. The shared documents arrive into memory, every text document is opened from what arrived, and `CollabStore.reconcile_plan` compares the disk against them, read-only, for the offer card: `same`, `differs`, `new here`, `new from peers`, `deleted elsewhere`. Accepting runs `reconcile_apply` in that order: a differing text file's local text is recorded as a version labelled "Before rejoining" under the live record's id; a differing binary, compared by size since that is all a record carries, and a file the others deleted go into this folder's trash, the latter under the trashed record's id so that `key_for`, which adopts a path with a file and no live record, does not bring it back for everybody as a new file; `last_projected` is dropped for every file the projection must rewrite, because `body()` left it holding the document's text and `_write` skips a file it believes it already wrote; and only then is seeding turned on and `adopt()` run for the files that are new here. Three kinds of folder are told apart before anything is dialled: an empty one is the join's own; one carrying `.nexttex/collab/docs` without this share's record was a project of its own with ids of its own, so that directory is moved to `.nexttex/collab.before-rejoin` and put back on discard; and one already holding this share's `share.json` and logs is opened rather than offered, since the logs are the sync state, while one holding another share's is refused. `JoinMade` records what the join created, and `_undo_join` removes exactly that on discard, on timeout and on failure.

**A git checkout merges three ways.** Where the folder is a repository and the file is tracked, `gitrepo.head_text` gives what `HEAD` holds, a base for the two sides, and `differs` splits: a file equal to its base carries no local edits and is `behind`, replaced with nothing recorded since git keeps it; a file whose edits since `HEAD` apply cleanly to the document under `gitrepo.merge_three`, which is `git merge-file -p` on three files in a scratch directory outside the project with the conflict count as its exit status, is `merged`, and the merged text is ingested as an edit made here so it reaches everybody, with the local text kept as the labelled version all the same. A merge with conflicts stays `differs`, because markers must never reach a shared `.tex`. `head_text` refuses a path that is absolute, that climbs, that begins with a dash or that carries a colon, since the path sits inside the one argument `HEAD:<path>` and `--` cannot fence it. Both read like `Path.read_text` would, CRLF as LF, and the three scratch files are written as bytes: written in text mode on Windows they carried CRLF into the merge and from there into a document that had never held a carriage return, which the last cross-machine leg found as a blank line after every line on the other machine.

There is deliberately no merge path for two divergent copies of one project beyond this: where a file differs and git holds no base, or the merge conflicts, the document wins, and what it replaced is kept where the writer can get it back.

A held join is state the server would not otherwise have, so it is bounded: discarded after ten minutes by the reaper, and released on shutdown.

**A folder that is gone is gone from one disk.** Nothing in the store asked whether the project root still existed, so `rm -rf` of a copy, a `mv`, or a drive going to sleep read as every file being deleted one by one, was published as such, and moved the whole project into every collaborator's trash. `CollabStore._root_present` is asked before a flush, before a deletion is flagged and before a log is appended, and once it says no the store flags, writes and logs nothing more and tells the session, which publishes `root_lost` and asks the server to close it. The watcher reports the folder itself when it is removed or moved, and finds a folder that went while nothing was watching when it next starts, so all three reach the same place; and because on Windows a deleted watch root produced no event at all, which the first cross-machine check found, the reaper looks at every open session's root once a minute as a backstop, and a peer's update reaching `_persist` is another. Because the root stands until its last file has gone, a batch of sightings naming half the project or more is held for one debounce and the root checked again before any of it is called deleted.

**What a peer may write is fenced.** A peer-supplied path goes through `resolve_for_write`, which refuses control files. Staying inside the project was never the whole question: `.git/config` is inside the project, and a `core.fsmonitor` entry in it is a command that runs on the next `git status`, which happens after every build.

**The wire has fifteen frame kinds, and an unknown kind is ignored.** `PeerLink.handle` is a chain with no else, so an install that predates a kind lets it fall through without a word, which is what lets a newer install talk to an older one and is what the five kinds added by the backlog run rely on. A link pings after twenty seconds of sending nothing and drops a link it has heard nothing from for sixty, at `PeerLink` rather than in the transport, because the loopback transport never times out and it is the one the test tier can sever without closing; the iroh transport's own read timeout stays as a backstop at ninety, having at sixty torn down every healthy idle link once a minute. A peer that connects and never says hello is let go under the same deadline. An ask for a blob or a file stands for thirty seconds and is then made again, and a `BLOB_MISS` or `FILE_MISS` is the other side saying it does not have the thing, which clears a blob ask at once and refreshes a file ask, since the file ask is automatic on every manifest sync and forgetting it would ask a sender whose record is there and whose file is not once per sync. A joiner, and any peer whose manifest names a binary its disk lacks, asks for it with `FILE_WANT`; the bytes go through the same `resolve_for_write` fence as text, are refused when nobody asked, when the path disagrees with the record, or when a file is already there, are parked in the store under a 512 MB bound and written by its flush rather than on receipt, and the session is told through `note_arrived` so the tree draws the file. A binary the watcher sees appear is adopted into the manifest at once rather than at the next open, since otherwise neither its past nor its bytes would travel until then.

**Every member is dialled from both ends.** A joiner dials everybody named in its `WELCOME`; a member who first hears of somebody through the manifest, in `mirror_members`, dials them too. Only the first half existed, so the newcomer's dial loop was the only thing that would ever rebuild a dropped link to them, and a peer whose member list had gone stale was never asked again. `adopt_link` replaces an older link for the same peer, which is what makes dialling from both ends safe.

**A removed peer is told by the tombstone, and only by the tombstone.** `PeerNetwork.remove` writes `removed_at` and `removed_by` into the manifest's member record in one transaction, so they travel as one update (as two, the removed peer acted on the first, closed its links, and never learned who removed it), which the observer queues to every link including the removed peer's, and then waits for that link's queue to drain (`PeerLink.drained`, bounded at two seconds) before closing it. A peer whose own record carries a tombstone, found in `mirror_members` after any manifest sync, runs `note_removed_self` once: links closed, transport closed, dial loops stopped through `removed_here`, `collab_peers` announced, and `state()` reports `removed` and `removedBy`. A `DENIED` from another peer is not treated as a removal, because a peer refuses from its own `share.json`, which can be behind; it marks the link `denied`, which the dial loop counts as a failed attempt for its backoff where a successful connect used to reset it, and it sets `last_error`, which a `WELCOME` clears.

**Leaving is a removal of oneself.** `PeerNetwork.leave` writes this install's own tombstone into the manifest, waits for every link to drain it, closes the links and the transport, clears the manifest's member list with no link open to carry the change (so `begin_sharing` later starts a fresh share rather than carrying the old members along), and removes `share.json` and the card, at which point `CollabStore.shared` is false again and the documents carry on as a private project's. `POST /api/projects/{id}/collab/leave` does that, and with `delete` closes the session, forgets the registry entry and removes the folder, refusing a folder that is the home directory, a filesystem root, or one with no `.nexttex/` in it, decided before leaving since leaving writes under `.nexttex/`.

**What a browser knows about the other end.** `PeerNetwork.state()` answers, per member, whether that peer's link is up, and `collab_peers` is published when a link is adopted or dropped so the browser hears the two ends of a connection rather than sampling for them. This is a different question from `connection` in the browser, which is that tab's own WebSocket to this server; both are drawn, separately, because a machine can have either one without the other and a writer who reads the wrong one believes their typing is arriving when it is not.

## The agent

One Claude session per project, driven from the browser, optional and off unless configured. Its working directory is the project root, so it cannot see NextTex's own source, and it loads the project's own `CLAUDE.md`.

**The OpenAI provider is a URL, and a local model is a different URL.** `nexttex/openai_agent.py` posts to `endpoint(base_url)`, which is `<base>/chat/completions` or OpenAI's own when `Settings.openai_base_url` is empty; Ollama, LM Studio, vLLM and most local servers serve that path, so a base URL in the settings is nearly the whole feature. No authorization header is sent without a key, since a local server wants none and some refuse a token they did not issue, and a base URL stands in for the key both in `ask`'s guard and in the status route's `ready`. A stream that carries no usage chunk, which local servers often omit even when asked, ends the turn with the footer's fields intact, since `_record_usage` only ever adds to them. `POST /api/agent/provider` takes `baseUrl`, absent for unchanged and empty for OpenAI itself, requires `http://` or `https://`, and with one requires the model named, because a local server has no default the way OpenAI does; switching to no agent forgets the URL along with the key. Since the backlog close-out the provider carries the three script tools behind a `PermissionGate` from `nexttex/permission_gate.py`, on the project's `agent-settings.json`, so it has `set_mode` and the three-position control; a script tool's call goes through the gate in `_run_tool` before `_dispatch`, and a no comes back to the model as the same sentence the Claude fence hands it. Its turn ceiling, `_within_budget`, counts only time with no card open, since a card has a timeout of its own, and `interrupt` answers every open card with no before cancelling the turn.

**The permission fence is a `PreToolUse` hook, not `can_use_tool`.** This was established by testing rather than reading: with `can_use_tool` supplied and no `allowed_tools` entry covering it, a Bash call still ran without the callback firing, in every permission mode. The SDK's own documentation names the reliable mechanism.

**A `/` at the start of a question is expanded once, in the ask route, and the transcript keeps what was typed.** `nexttex/prompts.py` holds the reusable prompts: two ship inside the package under `nexttex/prompts/`, `review-friendly` and `review-critical`, and a project's own are the `.md` files directly under `prompts/` at its root, where a stem that matches a built-in replaces it. The roadmap put them beside the distilled style guide, which is under `.nexttex/`; that directory is never synced and `initialise` writes it into the project's `.gitignore`, so a file there could not have been shared through git, which was the point, and `prompts/` at the root is what git sees. A stem is `[A-Za-z0-9-]` and nothing else, so a name is never a path, and a hyphen matches a space when typed. `prompts.expand` looks at the first line of the draft: a leading `/` followed by two words, then one, that name a prompt, case folded, and the rest of the draft is the writer's note. It runs in `agent_ask` before the provider fork, so both providers get the same thing: the file's text, with `The writer adds:` and the note when there is one, goes ahead of the selection in the context the turn is given, and the prompt handed to `ask` stays the line the writer typed, so the transcript on screen and in `transcript.jsonl` shows `/review friendly` and not three paragraphs of instruction. A `/` that names nothing goes through untouched. `GET /api/projects/{id}/prompts` lists both sources for the composer's menu and the Context panel, and `POST /api/projects/{id}/prompts/copy` writes a built-in into `prompts/<name>.md` through the ordinary save, so the copy has a version and the tree hears about it, and refuses a name that is already the project's own rather than overwriting an edited file. The scripted agent records the context each turn came with, and its `context` script says it back as the answer, which is how the browser spec sees the expansion without reading the server's memory.

**An image the writer hands the agent goes on disk, and the question carries the path.** Not for speed: it is the same arithmetic as the paragraph below. The agent already reads images from disk with its own `Read`, which is the path that was hardened, so there is no second image path to keep working; the transcript records a filename rather than a megabyte of base64; and a conversation that resumes by session id does not depend on the bytes being replayable, because they are still where they were. They land in `.nexttex/attachments/`, content addressed like everything else kept here, and the list of paths a question carries is checked against that directory rather than trusted, since it arrives as strings in an HTTP body and the one thing it must not become is a way to make the agent read an arbitrary path.

**A figure the agent reads costs more on the wire than the file does.** The SDK frames the CLI's stdout as one JSON line per message and refuses a line over a megabyte. An image tool result is base64, a third larger than the file, and the `PostToolUse` hook means the CLI ships it twice: once as a control request carrying the result to the hook, and once in the user message. A 290 KB figure measured 1.15 MB and killed the reader mid-turn, so `max_buffer_size` is raised well clear of any image the model would accept. Nothing is preallocated, so a ceiling that high only costs memory when a line really is that long.

**A client whose transport has died is thrown away rather than reused.** It is still an object, and its `receive_response` still returns, immediately and with nothing, so keeping it turns one lost answer into a conversation that replies to every later question in under two milliseconds with the news that the connection ended. Dropping it lets the next question build a fresh client, which resumes by session id, so the thread on screen survives what broke it.

**A client is reused only when the turn read its own result.** Stop tells the CLI to stop and leaves the reader in `_stream` running, so the `result` the CLI sends for the stopped turn is read and the turn ends the way every turn ends, with the SDK's buffer empty. It used to cancel the reader first and tell the CLI second, and the result then sat in the buffer, which lives as long as the client does: the next question's `receive_response()` yields the buffer before anything new and stops at the first result it sees, so it stopped at the stale one, three milliseconds in, while the real answer piled up behind it to be replayed as the answer to the question after. Every reply was one question late until the client was rebuilt, and once a hundred messages were waiting the SDK's reader blocked, the CLI blocked on stdout, and the model's own work was gated on the writer sending a message. Cancelling from outside is now the fallback, after `INTERRUPT_GRACE` seconds with no result or when the CLI could not be told, and a second Stop in that window is the fallback brought forward. Any turn that ends by cancellation, from that fallback, the silence watchdog, the subagent guard, eviction or shutdown, drops its client, because a buffer nobody can see into is not one to hand the next question; the session id is saved, so the fresh client resumes the same conversation. A stopped turn's result reaches the panel as `interrupted` whatever the CLI called it, since that is the word the transcript and the panel key on.

**Both post-tool hooks are registered, and only one of them used to be.** `PostToolUse` fires for a call that succeeded and `PostToolUseFailure` for one that did not, so with only the first registered a failed call never cleared the table of running calls. That table is what the watchdog reads, and a turn holding a phantom running call waits against the one hour tool timeout instead of the fifteen minute silence timeout, so a turn that died after a failed tool sat there for an hour. One handler serves both and reads `hook_event_name` to tell them apart, which is also what makes a `tool_done` event possible for every call rather than only the ones that worked.

**Two tools move what the writer is looking at, and neither changes anything.** `goto` publishes `reveal` and the editor opens the file at the line; `show_page` publishes `show_page` for a document on the preview strip and the browser puts that tab in front and turns the pane to the page, keeping the request until the document has that many pages when the switch and the page arrive together. The agent had `goto` and nothing for the preview, so one reviewing a long document could name a page and not show it. A name the strip does not hold is refused by the tool with the list of those it does, and by the session, so neither the tool nor a stand-in can announce a document the pane cannot show.

**The fence is also where the editor learns to follow.** On the branch that approves a write inside the project, the hook has just read the file to take the undo snapshot, so it knows both what the model is matching on and what it will match against: that is the only moment the landing line is knowable, because a second later the file has changed. A `focus` event carries the path and the line before the write happens, and carries nothing at all when the answer is not certain, since a highlight on the wrong paragraph spends the trust that the highlight means anything. Whether the view then moves is the browser's decision and it turns on whether this person has typed in the last three seconds, not on where the caret is: the caret sits in the editor for the whole time somebody is reading their own paragraph.

An agent edit is written to disk and then folded into the shared document, so the browser follows it live rather than being told to reload. If that fold fails, the file on disk is right and every browser holds text the agent has already replaced, which reads as the agent having done nothing, so the failure is logged rather than swallowed. A write that lands on one of the two summaries a distillation produces, `voice.md` or `style.md` in the context directory under `.nexttex/`, publishes `context_changed` from the same hook, because the watcher ignores that directory by design and the panel's "read these now" marker was otherwise computed from what it last saw.

The transcript is the record of what was done to the document: every edit with its diff, every reverted edit, and every command allowed, refused, or left unanswered. The third of those was missing and it is the one a reader would most want: a card that timed out was written down as refused, which is a statement about a decision nobody made. A turn also writes a `turn_end` record when it finishes, so a transcript that stops mid-sentence can be told from one that ended, without guessing from what the last record happens to be. It is an audit trail rather than session state, and it is what lets the panel survive a restart, since the model resumes its own memory by session id and would otherwise talk about "the sentence I added earlier" into an empty window.

**A figure is drawn by running a script, and it is one of six own-tools the fence asks about.** `run_plot_script` writes the script and runs it; `run_script` runs one already in `scripts/` by name without rewriting it, which is how a figure is re-drawn after the data or the style sheet changed, and it is fenced exactly as the first is, with the code on disk as the card's text. What an "always" on either remembers is the digest of the code the card showed, never the bare tool name: the bare name was the rule, so one yes on one script let every later script run silently while the agent's own `Write` into `scripts/` passed the middle position without a card. Installing a package is remembered by the package's name for the same reason. The spelling of those rules, the three cards' texts, the reason a card gives at the middle position and the notice for a card nobody answered live in `nexttex/permission_gate.py` since the backlog close-out, beside a `PermissionGate` that holds pending cards and remembered rules for an agent that does not have this file's own fence; the Claude agent keeps its fence and calls the module for those parts, so the two providers' cards for one script are the same card and an "always" given under either holds under both, because the rule names the code approved and not the model that proposed it. Most `mcp__nexttex__` tools are waved past the hook because none can reach the shell or a path outside the project. Installing a package is asked about wherever the network is, because pip downloads from PyPI and runs what it downloads. Three more can reach the network: searching the literature, adding a reference by DOI, and checking a bibliography against its publishers. They ask wherever a network tool asks, which is the first two positions, because the wave-past was written for tools that cannot leave this machine and these leave it with search terms and identifiers taken from the project's own files. The README's account of what leaves this machine lists them, so the fence and the README now agree. A tool that runs Python the model wrote can do both, and more than `Bash` can, so it is fenced like a shell call: asked at the first permission position and at the middle one with the script as the card's literal text, silent only at the last. The middle position is the one that says "the work runs without asking, and a write outside the project or anything reaching the internet still stops", and a tool that runs arbitrary Python is more than either of those: it went through silently for as long as the exclusion list named four answers and the code that built it named three. It runs with `sys.executable` and no shell, because that is the environment `requirements.txt` installed matplotlib into and the answer must not depend on the writer's shell; with `MPLBACKEND=Agg` and no `DISPLAY`, so `show()` cannot hang the run waiting for a window; with stdin closed, so an `input()` raises `EOFError` at once rather than waiting on the server's own terminal until the timeout; with the build's own timeout and its process group killed on it, and killed the same way when the task awaiting the run is cancelled, since a stop or a rerun otherwise left the interpreter running as an orphan; and with output clipped, for the reason images are clipped. The script is written into the project's `scripts/` directory through the ordinary agent write path, so it is versioned source the writer can change rather than a temporary file, and the run is verified rather than trusted: a script that exits zero having written nothing is the common failure.

## Running a script

A figure script is run by the agent's plot tool and, since the script pane, by the writer from the source pane; both go through `plots.run`. When what the script draws is wanted, the child interpreter runs `nexttex/script_runner.py` with the script as its argument rather than the script itself, and the runner is the one file in this package that executes in the child rather than in the server. It is standard library only, because it has to start whether or not matplotlib is installed, and it imports nothing of NextTex, because the first thing it does is replace `sys.path[0]`, which is its own directory and would otherwise let a project's `import config` find `nexttex/config.py`, with the script's directory, and set `sys.argv` to what `python scripts/fig.py` would give.

**What it keeps.** Every `pyplot.show()` saves the open figures as `figure-N.png` into the capture directory, in order, and closes them, so a script written for a screen shows its plots in the pane instead of in a window that will never open; every `Figure.savefig` is noted, so the pane can say which files in the project a run wrote; and a figure still open when the script ends, which is one that forgot to save and never called show, or one that crashed after drawing, is captured on the way out. The patches are installed from a `sys.meta_path` finder that wraps the loader of `matplotlib.pyplot` and `matplotlib.figure` and patches each the moment its `exec_module` returns, so a script that never plots pays nothing. A `module://` backend was not the answer, because the seeded `figure.py` calls `matplotlib.use("Agg")` itself and would override it; patching `show` after the fact is the one thing that survives that. Two details cost a try each. Importing the module from inside `find_spec` and answering None patched a module the import machinery then loaded a second time and handed to the script unpatched, which is why the loader is wrapped instead. And the final snapshot is taken in `main` rather than from `atexit`, because pyplot registers an `atexit` handler of its own when it is imported, which is after the runner started, so it ran first and closed every figure before the runner looked.

The runner writes `capture.json` beside the images, and `plots.captured` reads it without believing it: a figure name has to match the pattern the route serves, and a saved path is reported only once it resolves to a file inside the project. The result then carries `figures`, `saved` and `duration_ms` beside what it always carried.

**Around the run, per project, is `ScriptRuns`** in `nexttex/scripts.py`, owned by the session as `session.scripts`, and both the agent's plot tool and the writer's Run button go through it, so a figure the agent drew is in the pane too. It flushes the shared documents before every run, because the disk trails the editor by the debounce and the script the writer just edited has to be the one that runs; it publishes `script_start` and `script_done` on the event stream, so the pane in every window follows a run whoever started it, and between them `script_output`, what the script has printed so far, a frame per stream at most every 100 ms or sooner at 4 kB, bounded by the same 64 kB clip per stream the result carries, so a script printing ten thousand short lines in a second is ten or twenty frames and not ten thousand; the child runs with `PYTHONUNBUFFERED` so a print leaves it as printed, the reader takes chunks rather than lines so a single long line cannot overrun it, and past the clip it keeps reading and discards so a full pipe never blocks the child; and it keeps each script's last result under `.nexttex/runs/<slug>/`, emptied at the start of every run so a figure from last time cannot be mistaken for one from this time, where the slug is the path with its separators folded plus a short hash. ## History, trash and versions

**Content addressing.** A version is a sha256 of the file's bytes, stored once under that name, zlib compressed. Saving a file back to a state it has been in before costs nothing.

**Keyed by the file id.** Each file's log is a `<id>.jsonl` under the history's `log` directory, where the id is the collaboration manifest's, and `files.json` beside the logs maps id to path, former names and per-author purge floors; a `format` file there holds `2` once a store is keyed this way. The session binds the history to the store after adopting the project, and a history still keyed by path slug, which every store was until the backlog run, is migrated onto the ids then, once, through a staging directory so an interruption restarts cleanly. The store answers the key for a path: the live record's id, a fresh one after adopting a file the manifest has not seen, or the trashed record's id for a path with no file, which is what a purge of a deleted file's history and a restore from an old trash entry need. Versions are recorded off the loop, so the store answers that question from a worker thread by running it on the loop and waiting, since adopting writes the manifest map; and the history resolves a key before it takes its own lock, never under it, so a worker waiting on the loop can never hold the lock the loop is about to take. A history nothing binds, the bench's and a bare test's, keeps slug keys and `paths.json`. The wire speaks in ids and the history now listens in them, so a deletion's version reaches a peer through the same nudge as any other, where looking the file up by path had skipped its trashed record. The delete route flags the record itself rather than waiting for the watcher, so a file made under the same name in the next moment gets its own id and not the old file's past.

Every write NextTex knows about is recorded before the new text lands. This is not a replacement for git: it is what you want when you deleted a paragraph forty minutes ago and cannot remember what it said, at a moment when committing was the last thing on your mind.

Deleting is not a delete. An entry is written to the trash and the file is moved aside rather than removed, and moved rather than copied, so a folder of figures does not have to be compressed before it can be deleted. A file the watcher saw missing is not yet a file that was deleted: the collaboration store holds the sighting until its next flush and flags the record only if the file is still absent then, because a tool that rewrites by unlinking and recreating leaves exactly that gap, and the flag is shared state. Flagged at the sighting, it published a deletion to every peer and, at the flush, moved the file it found back on disk into this machine's own trash without a word. A file a peer really did delete still goes into the trash here, and the tree and the trash panel are told. A text file also gets a final version recorded in its own history on the way out, by the trash route and, since the backlog run, by the flush that flags a file the watcher saw removed; a figure or a dataset does not, so for those the moved-aside payload is the only copy and it is what protects them. Nothing is cleaned up on a timer, because a trash that empties itself after thirty days loses the thing you go looking for on day thirty-one.

Blobs nothing refers to are collected in four places: when the trash is emptied, when one trash entry is purged, when a file's history is cleared, and on a timer for every project that is open. That last one is not an optimisation. A shared project is deliberately never evicted, eviction used to be the only routine sweep, and so a shared project kept every thinned version's contents for ever unless somebody emptied the trash by hand.

**The browser hears about versions.** `History.listen` takes any number of listeners told a file's key when its log gains something; the peers were the only one, and the slot held one, so the session's listener would have replaced theirs. The session's publishes `history_changed`, naming every path whose log grew, `HISTORY_EVENT_DELAY` after the last of them, so a `git pull`'s forty files are one event; recording runs on worker threads, so the listener hops to the loop with `call_soon_threadsafe` first, and a session a test builds with no loop running skips it. The history panel refreshes its list on that event when the file on screen is named, and its size and the project timeline on any. Before it, the panel refreshed only after a build, which a `.md` never has. `tests/api/test_history_events.py` saves a `.md` through the file route with a subscriber on the stream and finds the event with no `compile_start`, and three files saved in one moment as one event.

## Where state lives

Inside the project, in `.nexttex/`:

| | |
|---|---|
| `history/` | content-addressed blobs, one log per file id, `files.json` and `format` |
| `trash/` | deleted entries, with a directory deleted as one entry |
| `collab/` | `share.json`, the document logs, cursors |
| `context/` | templates and style guides the agent is given |
| `attachments/` | images handed to the agent by pasting, dropping or picking one |
| `runs/` | each script's last run: what it printed, what it drew as PNG, and what it wrote |
| `library/` | the scanned bibliography folder |
| `transcript.jsonl` | the agent's audit trail, plus archived conversations |
| `session.json`, `agent-settings.json`, `usage.json` | per-project preferences |

In the install's state directory, outside every project: the instance token, hashed browser sessions, the OpenAI key if there is one, the project registry, `peer.key`, and under `shares/` one card per share this install is in, named by share id. Losing `peer.key` is losing the peer, not the work: the files are on disk and the collaboration can be joined again with a new invite.

**The share card** is `share.json` without the invites, written by `Share.save` every time the record inside the project is, and carrying the project folder's path. It exists because the moment somebody most needs to know whom to dial is after the folder is gone, and everything the install knew about the share used to go with it. `GET /api/projects` joins the cards to the registry by path, so a row carries `shared`, `shareId` and, when this install's own member record has a tombstone, `removed`, whether or not the folder is still there. The answer also carries `home`, the home directory of the machine running NextTex, because the rows fold it to `~` and the page may be open on another machine entirely. And it carries two lists of ids: `open`, every project with a session, which is a fact about the server since a session outlives the window that opened it by up to the idle timeout; and `watched`, the projects a browser is holding the event stream of at that moment, which is what a row means by "open in another window". The second list is only honest because leaving a project closes its stream: `leaveProject` in `App.tsx` used to close the document sockets and leave the stream to the tab's unload, so the project just left counted as held by a browser, and as in use to the reaper, for as long as the list was on screen. `Projects` also takes `current`, the id of the project the window came from, and never marks that row: the list's fetch on the way to the screen races the server noticing the closed stream, and the window that project is open in is this one. A share id names a file here, so one taken from an invite or a `WELCOME` is accepted only when it has the shape `begin_sharing` mints, `WELL_FORMED_SHARE_ID`.

A second install on the same machine is a named instance: `--instance NAME` at install time gives it `~/.local/share/nexttex-NAME`, a port derived from the name, a service called `nexttex-NAME` and a badge in the interface. The name reaches the process as `NEXTTEX_INSTANCE`, which the systemd unit and the launchd plist set in their environment. A Windows scheduled task, a Startup shortcut and a desktop shortcut on any platform are a command line and nothing else, so for those the name travels as `server/run.py --instance NAME`, which sets the variable before `Settings.load()` asks where the state directory is. Every launcher writes that argument; until it did, a named instance started from a shortcut or at login on Windows came up as the default instance, on the default port, over somebody else's projects.

Everything written through `write_atomically` goes to a sibling temporary file, is flushed to disk, and is then renamed over the target, with the directory flushed afterwards so the rename survives too. Renaming is atomic against this process dying and says nothing about the machine losing power: without the flush the rename can be on disk while the bytes it points at are still in the page cache, and the file comes back existing, the right length, and full of zeroes.

## Reporting a problem

`nexttex/report.py` composes the text a bug report carries: the commit the code is on and the commit the interface was built from, the settings with a yes or no where a secret would be, every tool the installer's own `survey()` looks for and where it found it, whether something supervises the process, what `claude auth status` says minus the account, a count of projects, and the last eighty lines of each log the install keeps. On Linux the server's output is in the user journal, so the report runs `journalctl --user -u nexttex` and quotes that; on macOS and Windows it is `server.log` and `server.err.log` in the state directory. `install.log` and `update.log` are quoted from their last `=== ` block, which is the run that just happened. On Windows the section goes on to what the system's own logs hold, `windows_events`: one PowerShell call, `-NoProfile -NonInteractive`, under a thirty-second ceiling, that first asks whether the Task Scheduler's operational log is enabled at all, because on a client Windows it is off until somebody turns it on and a report that said "nothing there" for a machine that keeps nothing would send the reader after events that were never written; then the task's events from the last week, filtered on the task's path; then the Application log's events from `Application Error` and `Windows Error Reporting` naming python, which is what a process that died with nothing logged leaves behind. Each block is bounded in count. The script is a plain string with no `@` in it, since a test holds the module to that, so the hashtable forms are spelled out as pipelines. `tests/test_report_windows.py` runs the real branch on the Windows runner and asserts it renders one of its shapes; everything else about it is stubbed in `tests/test_report.py`.

It is composed as one string and redacted once, at the end, over the whole of it. The pass replaces every secret value the config file holds (the token, the OpenAI key, the password hash and salt, each browser session's fingerprint), then any `token=` in a URL, then any line shaped like one of those keys, then anything that looks like an API key, then the home directory, which becomes `~`, and last the account's name, which becomes `[account]` wherever it stands as a word of its own, because a Windows event names the account as `DOMAIN\name` and journalctl as the name at the host, and neither is inside the home path the tilde fold reaches. Order matters: a secret never contains the home path, doing the path first would move the text under the patterns that follow, and the home path usually ends in the account's name, so the fold goes before the name. Doing it in one place is what lets one property test say the whole report is clean rather than one test per section.

Two constraints shape the module. It imports only the standard library at module level and runs as `python -m nexttex.report` on a bare interpreter, because a broken virtual environment is one of the likelier things to report and `server/run.py` imports uvicorn before it reads its arguments. And nothing in it opens a socket: `survey()` is asked not to probe the network, no update check is made, and the only thing that leaves the machine is the text the writer reads and pastes for themselves. It never reads `peer.key`, `key.pem`, `cert.pem`, a project's transcript, history or context, or any file of a manuscript; `projects.json` is opened for a count and its paths are not repeated. It never writes: the config is read raw rather than through `Settings.load()`, which creates the file when it finds none.

The same text is served at `POST /api/report`, where the browser adds what it saw: its user agent and a bounded list of its own last errors. The server composes the whole thing so that redaction has one choke point, since an error message on the client side can quote `window.location`, and that carries the token. The answer also holds the new-issue URL for the checkout's own GitHub remote (`updates.repository_slug`, falling back to the canonical repository when the remote is a local path), with the short facts filled into the form's fields and the report itself left for the clipboard, since a query string is capped by the server at the other end and the clipboard is not. The 500 handler's eight-hex reference is the join: it is in the message the writer saw and in the log line the report quotes. One section differs by entry point: `supervised()` and the two supervisor variables describe the process composing the report, which is the server from the footer and the terminal from `--report`, so the terminal report leaves those lines out and both ask systemd about the unit directly.

## The browser

React with a single mutable store read through `useSyncExternalStore`. A context and reducer tree would re-render the editor on every streamed token; this lets a component subscribe to exactly the slice it draws.

Three channels run at once. Ordinary **HTTP** for everything transactional. A **server-sent event stream** per project carrying `compile_start`, `compile_done`, `files_changed`, `trash_changed`, `history_changed` and a dozen more. A **WebSocket per open document** carrying the CRDT sync and awareness traffic.

The editor is CodeMirror 6; the preview is pdf.js; maths hovers are KaTeX. A table hovers too: `tableAt` in `frontend/src/panes/math-hover.ts` finds the `tabular`, `tabular*`, `tabularx` or `longtable` environment under the pointer once `mathAt` has said the pointer is not in maths, `parseTabular` in `frontend/src/panes/table-hover.ts` reads its column spec, rows, cells, rules, spans and inline maths (pure, so its tests need no browser), and the same tooltip draws the result as an HTML table with KaTeX setting the cells that are maths. Whether any of those cards is drawn is the writer's choice per browser: `appearance.ts` keeps `hover` (`nexttex.editor.hover`) and `hoverKinds` (`nexttex.editor.hover.hidden`, a comma list of the kinds turned off, so a kind a later build adds is on for a writer who chose before it existed, as every kind is until it is turned off), and `applyAppearance` stamps `data-hover-cards` on the root with the kinds that are on, space separated, or the empty string while the switch is off. `mathHover`'s source reads it through `hoverCards()` at the moment of the hover, a live read rather than a compartment: the source runs on every hover anyway, and the language compartment it sits in is never reconfigured (a file change makes a fresh state through `freshState`), so the setting takes effect on the next hover with nothing to dispatch. An absent attribute means every kind, so a bare document in a test draws every card; with the formula card off the cascade goes on to the table and the links rather than stopping, so a `\label` inside an equation still brings its cross-reference card; and the thing a `\ref` card draws under its line follows that thing's own kind. The editor's find and replace is the library's `search()` with the app's own panel, `frontend/src/panes/find-panel.ts`, a plain-DOM strip handed to `createPanel` that dispatches `setSearchQuery` as the fields change, walks the query's cursor to count the matches and say which one the selection is on, binds Enter on its two fields as the library's panel does, and hands every other key to `runScopeHandlers` for the `search-panel` scope; `Editor.tsx` measures `.cm-panels-top` with a mutation and a resize observer so the section bar sits under the panel rather than over it. The PDF pane, KaTeX, the collaboration client, the spell checker's word list, the tutorial, the upload card, the paper chooser, the file viewer, the version panel and the settings sheet are all fetched when they are wanted rather than before anything draws. Each of those is behind a click, and `bundle.initial_kb` counts only the entry script, so the test of whether something belongs out here is whether a session that never opens it should pay for it.

Every control is one of the kit's primitives under `frontend/src/ui/`, and a pane composes them rather than drawing its own: `Button` and `IconButton` (`frontend/src/ui/Button.tsx`), `Row`, `Field`, `Chip`, `ChipToggle`, `Switch`, `Segmented`, `Heading`, `Empty` and `Kbd` (`frontend/src/ui/controls.tsx`), `Menu` with `MenuItem` and `MenuDivider` (`frontend/src/ui/Menu.tsx`), `FloatingCard` (`frontend/src/ui/FloatingCard.tsx`), `Sheet` (`frontend/src/ui/Sheet.tsx`), and the one icon set (`frontend/src/ui/icons.tsx`, named exports and no table of them, so an icon a lazy pane imports stays in that pane's chunk). ## What is bounded, and by what

A single process with no database means nothing is bounded unless something bounds it. These do.

| | |
|---|---|
| Upload | 256 MB per file, 512 MB per request, 200 files |
| Request body | 512 MB, refused on `Content-Length` before the body is read |
| A file the editor will open | 10 MB |
| Idle agent | disconnected after 30 minutes |
| Idle session | evicted after 30 minutes, if nothing relies on it |
| Unanswered join | discarded after 10 minutes |
| Transcript | compacted by bytes, and 50 archived conversations kept |
| Build | 120 second timeout, then the process group is killed |
| A figure script, from the agent or from the source pane | 120 second timeout, then the process group is killed; 64 kB of output per stream; one run per script at a time |
| Installing a package | 300 second timeout |
| A file sent by a peer | 64 MB each, 512 MB parked in memory in all, held until the flush that writes it |
| A peer link | pinged after 20 s of send silence, dropped after 60 s of hearing nothing |
| A project search | 200 characters of pattern, 500 hits, and the regular expression runs in a thread |

## Security posture

Ranked the way the threat model is: an install may sit on a tailnet behind its password, and separately its project may have come from somebody else.

Enforced: origin on every unsafe method, two separate credentials with constant-time comparison, scrypt off the event loop, a rate limiter keyed on the socket address rather than a forwarded header, a content policy built from hashes of the two inline scripts this app really serves, blobs served as attachments with a fixed content type, control files refused on the peer path and on upload, `nexttex.toml` validated rather than trusted, `latexmk -norc`, option-shaped arguments kept away from `git` and `gh`, and delegation refused under both of its names, before any branch that could allow it and again for any call that arrives from inside one. The environment git is given is built from nothing rather than inherited, for the same reason: it carries `PATH`, `HOME`, `LC_ALL`, the two variables that stop git waiting for a password nobody will see, the ssh agent's socket, and `SystemRoot`, which is what the Windows socket stack needs to resolve a name at all. The SDK is also started with `strict_mcp_config`, so a project carrying its own `.mcp.json` cannot add tool servers to the session: a project is somebody else's data, and a file in it that names a program to run is the same class of thing as a `nexttex.toml` that names a compiler.

`/api/browse` is the one route that reads the disk outside any project, and it is not fenced to one on purpose: a project is already an absolute path typed into a box on the projects screen, so the folder picker behind that screen's Browse button and the papers chooser reach what the box reaches. What holds it instead is its shape, which `tests/api/test_browse.py` asserts: it answers folder names and, when asked, PDF counts, never contents; it does not follow symlinks; a file or a missing path is refused; and no tool the agent can call reaches it. The `pdfs` flag is a cost switch rather than a permission: counting opens every child of the folder being looked at, which the papers chooser wants and the project picker, opening on home, does not.

Project-wide search is the one route that compiles a regular expression written by whoever is holding the keyboard. Python's `re` has no timeout and a short pattern can backtrack exponentially, so the pattern is capped at two hundred characters, escaped unless a pattern was explicitly asked for, and matched in a worker thread: a pathological pattern then costs a worker rather than stopping every other request on the install.

**One thing is not fixed, and it is written down rather than claimed.** `openin_any` is passed to the engine and the pdfTeX this was tested against ignores it, under `a`, `r` and `p` alike, through the environment and through a `texmf.cnf`. Writes out of a project are refused; reads into it are not. A hostile source file can therefore read what the server's user can read and write it into a project file, which on a shared project reaches every peer. No amount of code here closes that.

## Testing

Four tiers, described in `docs/testing.md`. The short version: `scripts/check.sh` runs types, the frontend unit tests and the Python suite; `--all` adds the frontend build, the bundle budget and the browser tier; `--bench` runs the rest of the budgets against a thesis-shaped project.

The bundle budget is in `--all` rather than in `--bench` because it is a property of `frontend/dist` and needs nothing else: no synthetic thesis, no minute of LaTeX. It lived only in the benchmark tier, which is started by hand, and was therefore over budget for an unknown length of time with every routine check passing. A budget nothing routine looks at is a comment.

The Python suite needs nothing but Python. The agent is replaced by a scripted one, the network by the loopback transport, and the compile tests assert the command line rather than running an engine, so CI installs no TeX. Tests that genuinely need a TeX tool skip when it is absent, and put the tree on `PATH` before deciding to skip, or they skip on the one machine they were written for.

The installer is in that suite too, which it was not for a long time. `scripts/install.sh` and `scripts/install.ps1` are bootstraps that stop at the handover to `python -m nexttex.install`, and that package is standard library only because it runs before there is a virtual environment. `survey()` takes its platform as an argument rather than detecting it, so a machine of any of the three kinds is a case a test can construct; `Console.run` is the only place a child process is started, so a whole install is a list of argv to assert on; and the shell bootstrap is driven for real, under dash and at a controlling terminal made with `pty.fork`. `nexttex/install/steps.py` is imported by the running server as well, which is why its standard-library-only constraint has a test of its own: installing the Claude CLI from the settings sheet has to be the same act, and the same code, as installing it during the install.

What none of that can answer is whether the documented command works on a machine, and `.github/workflows/install.yml` is the tier that asks. On a schedule and on demand, it feeds the checkout's `install.sh` to `sh -s` the way `curl | sh` would on ubuntu and macOS runners, pipes `install.ps1` through `iex` under Windows PowerShell 5.1 and runs it from the checkout under pwsh 7, installs the previous commit from a bare copy and updates to this one with the update scripts, runs the shell bootstrap inside Debian, Alpine, Fedora and a container with no Python, and runs the browser tier's update spec against the install it just made. `tests/lane/verify_install.py` holds the assertions, which are the README's own claims: the venv imports the app, the interface belongs to the commit, `install.log` names every step, the address prints, `/api/instance` answers with the right head and refuses a wrong token, the service file is where the README says, a second run appends one block to the log and changes nothing else, and the README's uninstall commands leave nothing behind. It runs on the runner's bare interpreter, imports only the standard library, and is not collected by pytest, because what it needs is a machine that was clean five minutes ago. Its first runs found the uv branch of the bootstrap had never worked, the log held half of what it claimed, and three of the scripts needed a bash that Alpine does not have, so every shell script the installer or the server runs on a machine is POSIX sh now, checked under dash and by shellcheck in the per-push job.
